# SOLACE Garden UI conventions

These focused conventions capture patterns demonstrated by the current shell. They are not a comprehensive design system; feature-specific components should be added only when a real workflow needs them.

## Milestone UI consistency review

**Purpose:** Treat this document as the authoritative record of **reusable, approved, application-wide UI conventions**, not a complete design system or a log of every screen-specific choice. Apply existing conventions across features so separately implemented milestones form a coherent application.

- **Before UI implementation:** Review relevant conventions here and walk through the feature's entry points, navigation, and interactions with adjacent existing workflows. Follow established patterns unless a specific need justifies a departure.
- **At milestone review/acceptance:** Ask these three questions:
  1. **Did we establish any new reusable UI conventions?**
  2. **Did the implementation reveal inconsistencies with existing conventions?**
  3. **Should any decisions be documented for future milestones?**
- **Record only decisions that have actually been approved or demonstrated.** Add a concise rule and its scope here when it will apply across screens. Keep milestone-specific requirements and acceptance findings in their owning documents (such as `UI_REDESIGN.md` or `UI_REVIEW_NOTES.md`), and speculative enhancements in `PARKING_LOT.md`. Do not turn a proposed pattern into a universal rule automatically.
- **Handle mismatches deliberately:** Correct significant functional, accessibility, or usability inconsistencies within the relevant scope; record nonblocking visual polish for its planned review rather than expanding an unrelated milestone. Document any intentional, justified exception without forcing every UI into identical layouts.
- **No change needed is a valid outcome.** Do not edit this file, reopen accepted designs, or initiate broad refactors solely to satisfy the review checklist.

## Visual palette and link/button states (design baseline; Step 10 review pending)

The current implementation's baseline tokens are defined in `src/style.css`: warm background `--sg-color-background: #f7f5ee`, white surface `#ffffff`, botanical primary `--sg-color-primary: #486747`, stronger green `--sg-color-primary-strong: #365235`, soft green `#e5ede2`, dark text `#29342b`, muted text `#647066`, border `#d7ddd3`, and focus `#8eab78`. **The stylesheet is authoritative for implemented values**, not this list.

### Preserved palette candidates (not yet selected for V1)

Keep **both** of these Garden palette candidates available for side-by-side visual trials in Step 10. Color chips alone are insufficient to approve a theme: a palette can look attractive as swatches but be unpleasant or illegible on actual buttons, navigation, forms, cards, and interactive states. **Neither palette is approved as the final UI theme**, and these records do not authorize immediate CSS changes.

**Step 10 selection process:** Show each candidate in representative live UI contexts, particularly primary/secondary/destructive buttons, links and breadcrumb hover, sidebar active/hover states, headings, cards, and forms. Test contrast, focus visibility, disabled states, and both mobile and desktop layouts. Compare those results with the currently implemented CSS palette. Make the final decision **after visual review in the browser**; then update semantic tokens and document the chosen convention.

**Shared interaction convention to validate in Step 10:** Text links, breadcrumb links, navigation links, and button-like links should draw from a coherent, accessible set of semantic colors and states (default, hover, focus-visible, active/current, disabled). Breadcrumb parent links must have a clearly perceptible hover state; the current very pale gray hover is a usability issue. An inactive/current breadcrumb item is not an interactive link. Preserve meaningful distinction between navigation links and action buttons, and do not require every control to use identical styling. Audit contrast in ordinary and hover states, and use more than color alone for state. Prefer shared semantic tokens/global rules over page-specific hardcoded hover colors after visual approval.

**Layout alignment to validate in Step 10:** Page-level breadcrumbs, eyebrow, title, and description should share a stable horizontal alignment anchor while forms and card grids may use different widths. A reusable page-header pattern can help, but must be placed in a shared page layout rather than inside differently centered content containers. See `docs/UI_REDESIGN.md` Step 10 for the observed Create Garden/Quick Start jump.

## Typography (current baseline and future review)

**Status:** No final application-wide typography design has been selected. Prioritize functional development; evaluate font treatment with the other Step 10 visual refinements rather than changing it now.

**Current implementation:** `src/style.css` declares `font-family: Inter, ui-sans-serif, system-ui, -apple-system, BlinkMacSystemFont, "Segoe UI", sans-serif`, with root `line-height: 1.5` and `font-weight: 400`. This is a font *preference stack*, not evidence that Inter is bundled or loaded; the visible face may fall back to the user's system sans-serif. The CSS remains authoritative for implemented typography. Bootstrap 6 typography conventions and utilities are the preferred baseline for semantic headings, text sizing, weights, and spacing: [Bootstrap 6 typography](https://getbootstrap.com/docs/6.0/content/typography/).

**Branding reference:** The existing SOLACE Garden SVG wordmark has an organic, serif-like visual character. Its letterforms are embedded as SVG paths, so it does not establish an application font family or require a matching font to be installed. Consider whether a complementary serif for selected headings would create a warmer gardening/journal feel while leaving body text, controls, and dense forms in a highly legible sans-serif. This is an **option to test**, not an approved font pairing.

**Options to compare during a later visual review:**
- Bootstrap's native system font stack, avoiding extra font assets and improving platform familiarity.
- A deliberately bundled, locally served font family (for example one sourced under suitable terms from Google Fonts), allowing more uniform appearance while considering file size, offline PWA caching, licensing, and fallback.
- A restrained serif-heading/sans-serif-body pairing if it complements the wordmark without undermining readability.

**Questions for approval:** Which typeface(s) suit the brand on actual pages? What should the consistent `h1`–`h6` hierarchy, body, secondary text, form labels, and buttons look like? How should font sizes, line heights, weights, text wrapping, and responsive scaling behave? Test on desktop and mobile, including readability outdoors and at increased browser text/zoom settings. Maintain semantic heading order independently of visual size. Make a final choice only after viewing representative app pages in-browser.

## Theme Architecture and Future Customization

**Status and intent:** V1 ships **one default visual theme**, selected after the Step 10 in-browser review. Make the CSS **theme-ready** without shipping a theme switcher, font picker, theme directory, user-provided assets, or extra theme management in V1. Future appearance options are independent of Simple/Standard interface modes, routes, functionality, and stored Garden data.

**Separate structure from appearance:**
- Core Garden/component CSS owns layout, responsive behavior, sizing, spacing, positioning, and interaction mechanics; theme definitions own colors and font choices through **semantic CSS custom properties**. The specific future filenames (for example `garden.css` plus `themes/default.css`) are illustrative, not a required file move or new architecture for V1.
- Components should consume shared `--sg-*` tokens for text, surfaces, borders, links, actions, states, and typography rather than embed palette values or hardcoded font families. Prefer semantic roles such as link/default/hover, primary-action/default/hover, muted text, focus, danger, and background over color-name variables. Respect accessibility and legibility in each state.
- Keep Bootstrap 6 controls aligned with Garden tokens through appropriate Bootstrap CSS variable overrides, without altering the structural component rules per theme. The default theme should preserve the chosen V1 appearance. The current `src/style.css` tokens are a starting point, not yet a fully audited separation of styles.
- Distinguish **color theme** from **font preference** so changing one need not create a new combined theme variant. Use fallbacks for fonts, and keep semantic markup and layout usable if custom appearance assets fail to load.

**Step 10 prerequisite review:** Audit existing application stylesheets and component styles for hardcoded color values, font families, hover/active/focus/disabled treatments, Bootstrap default colors leaking into Garden components, and styling that mixes theme values with layout. Identify reusable semantic tokens and the smallest sensible path to separating appearance from structure. Review actual pages in-browser before choosing the default palette or undertaking a broad CSS refactor; preserve accepted behaviors, accessibility, and responsive layouts. Document approved conventions here. This is **planned review work**, not an instruction to interrupt ongoing functional milestones.

**Future version direction (provisional, not V1 requirements):**
- **V2:** Consider a small, curated appearance menu: approximately **2–3 built-in color themes** and **around seven font options**. The user picks what is most comfortable; test these options on actual buttons, forms, headings, Garden records, and mobile/desktop screens. Keep selections local and compatible with offline-first operation. Exact options, defaults, implementation, and version scope remain to be decided.
- **V3/V4 or later:** Explore **third-party pre-made themes and fonts** installed by copying files into a designated theme/font directory for a supported deployment (a possible hosted-site path is `/assets/user/themes/`). The application would discover available themes, offer them in Appearance settings, and **validate submitted CSS against a defined theme schema/contract**, rejecting noncompliant themes. Always retain the built-in default theme as a fallback if a third-party theme is invalid, incompatible, or missing. The initial scope might be the hosted web version at `garden.solace.network`; **offline PWA support can follow later** after its storage, discovery, and caching approach is designed. The manifest/discovery mechanism, validation rules, security boundaries, font-file handling, and deployment details remain open for future discussion. A browser-installed PWA cannot assume direct access to arbitrary local filesystem directories.

**V1 boundary:** Implement and validate the single default theme, while avoiding unnecessary styling dependencies that would force edits to core layout rules for future palette/font variants. Do not build a speculative theme engine.

## Controls and focus

- Use native links for navigation and native buttons for actions. Do not add `tabindex` to elements that are already interactive.
- Icon-only controls need an accessible name through `aria-label` or visually hidden text. The shared `.icon-control` convention provides a 48 × 48 CSS-pixel target; the visible icon remains `aria-hidden="true"`.
- All custom interactive controls use a visible `:focus-visible` outline based on `--sg-color-focus`. Do not remove native focus behavior unless an equivalent visible treatment replaces it.
- Bootstrap Icons are the application icon set. State and meaning must also be communicated through text or accessible naming rather than color or icon shape alone.

## Dialogs and fullscreen editors

- Use Bootstrap 6 `Dialog` with a native `<dialog>`, not Bootstrap 5 Modal markup. Initialize after mount, remove application listeners, and call `dispose()` on unmount.
- Focused editors may use `md-down:dialog-fullscreen`; wider screens may use a conventional centered Dialog.
- The upper-right `.btn-close` is an empty element with an accessible label and an approximately 48 × 48 target. It always means Close/Cancel, never Save.
- Preserve the Plants quick-close guard: if Close is requested during the opening transition, hide immediately after `shown.bs.dialog` rather than dropping the request.

## Close, Save, and unsaved changes

- Close and Cancel return to the prior working context. They must not save or silently discard dirty data.
- Future data-entry screens use explicit Save/Done actions. Save stays disabled when content is invalid or unchanged, stays available while persistence is pending, and reports success only after the repository confirms the write.
- Dirty screens require confirmation before route changes or destructive close. Add `beforeunload` only while dirty, recognizing that browsers may suppress it. Implement this with a real editor workflow rather than a speculative global state manager.

## Feedback states

- Empty states explain what is absent and offer the next meaningful action when one exists.
- Loading states identify the content being loaded and use `aria-live="polite"` only when an announcement is helpful; avoid indefinite spinners without text.
- Recoverable errors keep the user's input, state what failed in plain language, and provide a retry action where meaningful. Validation errors are associated with their fields.
- Create a shared feedback component only after a real data-backed page demonstrates repeated empty, loading, or error markup.

## Contextual Drawer

- `AppDrawer` provides a reusable Bootstrap 6 `Drawer` on a native `<dialog>`. The default Information trigger remains for optional secondary information, not a substitute for a fullscreen editor. Standard Mode also uses a custom trigger for its phone and medium navigation overlay.
- Required props: `id` (unique dialog ID) and `title` (visible heading and accessible name). `placement` accepts `top`, `end`, `bottom`, or `start`; omitted or invalid values use `bottom`. Start/end follow the document direction.
- `children` supplies drawer-body content, or a render function receiving `{ close }` for content with its own close action. The labelled header close control and footer Close button are always provided.
- `triggerLabel` defaults to `Information`. Optional `renderTrigger(triggerProps)` replaces the fixed Information button. Render a native button and spread **all** supplied props onto it: `ref`, `type`, `onClick`, `aria-controls`, `aria-expanded`, and `hidden`. Give the button visible text or an accessible name, visible focus, and a roughly 48px touch target. Do not override the hidden state or add Bootstrap data-toggle attributes that would open the same instance twice.
- The invoking trigger is hidden during opening/open/closing. Close during opening is deferred until `shown.bs.drawer`; focus returns to the original connected trigger after dismissal. Pending focus restoration is cancelled on reopen/unmount. Listeners are removed and the Bootstrap instance is disposed on unmount, including while open.
- The header Close control uses native `autofocus` for initial focus. After `shown.bs.drawer`, focus is moved there only if it remains outside the dialog (the pinned alpha’s visibility transition can prevent native autofocus). This is a one-time correction, not a focus trap. Bootstrap owns modal focus entry/trapping, Escape/backdrop dismissal, scrolling and reduced-motion transitions. Do not add a second focus trap. Consumers must unmount/remount the drawer to change placement while it is in use (Bootstrap initializes swipe direction on first opening).
- Top/bottom are full-width at roughly 45% of dynamic viewport height on mobile and 40% at `md` and up, with `vh` fallback. Side drawers are full-height and default to 300px wide, constrained by Bootstrap to the viewport. Surface, close controls, inner scrolling and safe-area spacing are shared; corner rounding faces the content area.
- Override dimensions with `--app-drawer-height` or `--app-drawer-width` on the dialog via CSS (for example `#garden-info`) or the optional `style` prop. Defaults remain unchanged for existing bottom-drawer callers. Reassess dimensions with real content before broad reuse.

```jsx
<AppDrawer id="garden-info" title="Garden information">
  <p>Contextual information</p>
</AppDrawer>

<AppDrawer
  id="custom-panel"
  title="Panel"
  placement="start"
  style={{ '--app-drawer-width': '280px' }}
  renderTrigger={(triggerProps) => (
    <button class="icon-control" {...triggerProps} aria-label="Open panel">
      <i class="bi bi-list" aria-hidden="true"></i>
    </button>
  )}
>
  {({ close }) => <button type="button" onClick={close}>Done</button>}
</AppDrawer>
```

## Standard Mode navigation

- `StandardNavigation` resolves `standardPrimaryIds` through the destination registry: Gardens, Journal, Gallery (`photos`), PlantDB (`plants`). Display overrides stay local to navigation. Templates remains a direct route and uses the Gardens navigation context, but its entry point is the contextual Templates action on `/gardens`, not a nested Standard navigation item. Home uses the shared data-backed dashboard, with Simple Mode cards above it.
- At `lg` (1024px) and above, the expanded sidebar has a fixed 300px width/flex basis. At `md` (768px) through 1023px, the iconbar has a fixed 60px total width, four direct 48px icon links with accessible names/titles, and an explicit Open navigation button. Current links use `findRoute(path)`, `aria-current="page"`, and a visible dot in addition to color; `/templates` marks Gardens with `aria-current="location"` to communicate its contextual parent without claiming that `/gardens` is the current page.
- Phone and medium navigation share one `AppDrawer` with `placement="start"`, title Navigation, and `--app-drawer-width: 300px`. On medium screens its total width overlays the iconbar and 240px of workspace; it never changes workspace dimensions. Forward all native trigger props. Normal link activation calls the render-function `close()` without preventing routing; modified activation leaves the Drawer open.
- Match-media presentation changes unmount the Drawer, allowing AppDrawer/Bootstrap to release native modal state. If navigation held focus, restore it to the corresponding visible link (Gardens when a secondary destination has no icon). Entering the phone presentation focuses its visible Navigation button. Small/medium presentation changes key the shared AppDrawer by presentation, closing and remounting it through the existing disposal lifecycle; resizing within either range retains the instance. If StandardNavigation itself disappears, the logo is the focus fallback. This handles removed controls only; AppDrawer owns ordinary dismissal and focus restoration, with no additional focus trap.
- Below 768px, effective Standard shows a compact, non-sticky strip in normal flow directly below the Header. Its 48px Navigation button opens the shared 300px start Drawer (constrained to the viewport); a separate noninteractive, ellipsized label uses `findRoute(path)` and navigation display overrides, with Navigation for unmatched routes. The strip retains its height while AppDrawer hides its trigger, so modal interaction does not move the workspace. The obsolete Browse workspaces disclosure is removed. Automatic/Simple/Standard resolution and persistence remain independent of navigation presentation. The generic global About this workspace disclosure is removed; contextual information belongs to feature pages.

## Simple Mode navigation cards

- `simpleCardIds` defines Simple Mode placement and order; resolve each destination through `findRouteById()` so registered paths and icons remain authoritative. Keep presentation-only label overrides local to the card component.
- A navigation card is one native anchor covering the complete surface, with a visible Bootstrap Icon and text label. Do not nest buttons, links, or feature actions inside it, and do not add data loading or persistence to navigation cards.
- Gardens is the featured first card and spans the complete grid. The remaining cards use two columns below `md` and three columns at/above `md`; retain DOM order as visual and keyboard order. Center and cap the overall content width instead of adding more desktop columns.
- Cards have a minimum 48px target, visible `:focus-visible` treatment using `--sg-color-focus`, legible wrapping at narrow widths, and no information available only on hover. Disable decorative movement for reduced-motion preferences.

## Card carousels

- Use the shared `CardCarousel` for horizontally scrolling card collections. Its public contract is `children`, an accessible `label`, and optional `id` and `className`. Do not add record-specific behavior to the shared component.
- The parent owns data retrieval, loading and error states, filtering, sorting, empty-state copy, and actual card markup. Supply stable Preact keys for collection items. The carousel does not access services, storage, routes, or application-wide state.
- `CardCarousel` owns Bootstrap 6 initialization/disposal, native scrolling and snapping, stop-at-ends Previous/Next controls, measurable overflow, and responsive presentation. Multiple instances are independent; omitted IDs use a stable component-instance ID.
- Direct slide additions, removals, and keyed reordering recreate the local Bootstrap instance after disposing the old one. Updating content inside a card or rerendering an equivalent keyed collection must not recreate it.
- Responsive item counts are based on the component's available inline size through container queries: two cards when narrow, fractional 2.5/3.5/4.5 presentations at intermediate widths, and up to six when at least 64rem is available. Parent card components own their content layout and height.
- Hide the complete control group when every card fits. Bootstrap owns boundary disabling, keyboard movement, native touch gestures, reduced motion, and active-slide state. Do not add a second gesture engine, focus manager, or boundary-state implementation.
- Give every carousel an accessible label. The rail is a named carousel region, controls are native labelled buttons, and structural wrappers are not tab stops. Callers must provide keyboard-accessible card actions and visible focus styles where cards are interactive.
- A zero-child carousel is safe, but the parent normally decides whether to render it and owns any explanatory empty state.
